### FIX 0 — Storage shows "NaN undefined / 2 GB" on the dashboard, account, and storage cards
**Cause:** a storage value is read as `undefined` (the API field is missing or named differently) and then formatted, producing `NaN undefined`. It currently appears on every screen that shows storage.

**Fix:** never format a raw storage value without guarding it. Compute used/total safely and show a skeleton or `0 MB` until real data arrives — never `NaN`.
```ts
// Safe storage formatter — use everywhere storage is displayed
function formatStorage(usedBytes?: number, totalBytes?: number) {
  const used = Number.isFinite(usedBytes) ? (usedBytes as number) : 0;
  const total = Number.isFinite(totalBytes) ? (totalBytes as number) : 0;
  const fmt = (b: number) =>
    b >= 1e9 ? `${(b / 1e9).toFixed(2)} GB`
    : b >= 1e6 ? `${(b / 1e6).toFixed(1)} MB`
    : `${(b / 1e3).toFixed(0)} KB`;
  const pct = total > 0 ? Math.min(100, (used / total) * 100) : 0;
  return { usedLabel: fmt(used), totalLabel: total ? fmt(total) : "—", pct };
}
```
- Audit the storage API response and map the correct fields. If a value genuinely isn't loaded yet, render a `<Skeleton>` — never a computed string.
- The cap shown is "2 GB" but the Builder tier is 1 GB (Part 4). Pull the displayed cap from the user's actual plan, not a hardcoded number.

### FIX 1 — Pi Domains navigation shows "An unexpected error occurred while authenticating"
**What the screenshot actually shows:** the error appears on **Pi's own Domains page** after the hand-off from the app — not inside Sherry. Part of this is Pi-side (Pi's Domains service authenticating the user), which your code cannot fix. Your job is a clean hand-off. **Verify the split:** open the same Pi Domains URL **directly from the Pi Browser** (not from Sherry). If it errors there too, it is a Pi-side/transient issue — not your bug, and not worth burning hours "refactoring."

**Cause (the part you control):** the "Get a .pi domain" / "Open Pi domain portal" action is being routed through the app's internal router and/or is triggering a Pi SDK auth call (re-running `Pi.authenticate` / re-init) as part of opening the link. External navigation must never touch Pi auth or the SPA router.

**Fix:** open the Pi Domains URL as a **plain external navigation, fully decoupled from auth and routing.** The Pi Browser authenticates natively on the destination — the app only hands off the URL.
```ts
// lib/openExternal.ts
// Opens an external URL (e.g. the Pi Domains portal) WITHOUT touching Pi auth or the router.
export function openExternal(url: string) {
  // Do NOT call Pi.authenticate(), Pi.init(), or any Next router here.
  // Hand the URL straight to the Pi Browser and let it authenticate natively.
  const win = window.open(url, "_blank", "noopener,noreferrer");
  if (!win) window.location.assign(url); // fallback if the webview blocks window.open
}
```
- The domain buttons call `onClick={() => openExternal(PI_DOMAIN_PORTAL_URL)}`.
- **Never** use Next.js `<Link>` for this URL — use a plain handler or `<a href rel="noopener noreferrer" target="_blank">`.
- **Never** gate this navigation behind an auth check, and **never** re-authenticate on the click or on return.
- On return to the app, **reuse the existing session** — check for an existing access token first; only call `Pi.authenticate` if there is none. Don't blindly re-auth on mount.
- **If the error persists after a clean hand-off, it is on Pi's Domains page, not Sherry.** Surface a friendly note ("Pi's domain portal is having trouble — try again shortly") so a Pi-side failure never looks like a Sherry bug.

  document.cookie = `pi_env=${env};path=/;max-age=31536000;samesite=lax`;

export async function handleEnvSwitch(newEnv: PiEnv) {
  if (newEnv === getEnv()) return;                       // idempotent
  // LIVE confirm is a bottom sheet (header stays visible); TEST needs no confirm.
  if (newEnv === "mainnet" && !(await confirmMainnetBottomSheet())) return;
  setEnv(newEnv);

## 4. TIER & VALUE MODEL — implement exactly as written

### The logic behind the pricing structure
**Two revenue streams doing two different jobs:**
1. **Subscriptions** cover infrastructure costs (storage, pinning, bandwidth). Each paying user covers their own footprint plus margin.
2. **Pi payment fees** are the profit engine — near-pure margin, because the platform is already intermediating payments. This stream scales with the entire Pi economy flowing through hosted sites, not just with user count.

**Numerology pricing — every price reduces to 8.** Each paid tier's monthly Pi price has digits that add up to 8: **Builder 17 → 1+7 = 8 · Pro 35 → 3+5 = 8 · Business 134 → 1+3+4 = 8.** Annual prices keep the pattern automatically, because ×10 just adds a zero: **170 · 350 · 1,340 — still 8.** This is a deliberate, memorable structure for the brand. The absolute Pi numbers are still tunable (Pi's fiat value is volatile) — **if you rescale them, keep each one reducing to 8.**

**Why the structure matters more than the exact number:** Pi's fiat value is volatile. The *structure* (each tier ≈ 2–4× the value of the one below) stays correct no matter what Pi does. Tune the absolute Pi numbers against real cost and real Pi value; keep the digit-sum-8 pattern. Do not hardcode them as permanent.

**The fee ladder that drives upgrades:** every hosted site can accept Pi payments from its visitors (tip buttons, paywalls, gated content). The platform takes a small fee on that Pi, and **the fee drops every tier — 5% → 3% → 1.5% → 0.5%.** Once a user is earning Pi through their site, upgrading pays for itself in lower fees. Someone earning 200 π/month saves more than the Pro subscription costs, just in fees — the upgrade is an investment, not a splurge.

### The 4 ways Sherry makes Pi (one platform, four income streams)
This is the real "money machine" — not gimmicks bolted into the app, but **four genuine revenue streams the platform runs on.** Build the tiers so all four are switched on:
1. **Subscriptions** — developers upgrade to Builder / Pro / Business, paid in Pi, monthly or annual.
2. **Payment fees** — a small slice of the Pi that hosted sites earn through the built-in Pi payments (5% → 0.5% by tier). This scales with the *entire Pi economy* flowing through Sherry, not just signups.
3. **Pi domain connections** — premium `.pi` domain slots and connection features on paid tiers.
4. **Marketplace** — featured listings, premium templates, and boosted placement; creators sell, Sherry takes a cut.

The tiers below are the **consumer-facing packaging**; these four streams are how that packaging turns into Pi. ## 5. PI DOMAIN INTEGRATION — the centerpiece feature (build the full loop)

This is what makes Sherry native to Pi instead of generic IPFS hosting. The whole loop runs inside the Pi Browser.

### The user flow — must feel seamless
1. Every project shows a **"Connect a Pi domain"** card in the Projects view.
2. If the user doesn't have a `.pi` domain yet, show a **"Get a .pi domain"** button that opens the **official Pi Network domain registration and auction portal** directly in the Pi Browser.
   - **Open via a standard `<a href="{PI_DOMAIN_PORTAL_URL}" target="_blank">` or `window.open(url)`** — the Pi Browser handles navigation natively.
   - **Do NOT use an iframe.** The Pi domain portal handles its own auth and payment flow.
   - **IMPORTANT:** `{PI_DOMAIN_PORTAL_URL}` is a placeholder. The developer (Brenden) must fill in the exact official Pi domain portal URL from the previous build. Do not guess or use a third-party URL.
3. User buys or claims their `.pi` domain on Pi, then navigates back to the app.
4. Back in the app, they **paste their domain** (e.g. `beejayy.pi`) into the domain input field and tap **"Connect domain."**
5. The app **verifies they own the domain** (see backend spec below), maps the domain to the project's current IPFS CID, and shows the connected state.
6. **From that point forward: every redeploy automatically updates the domain to the newest CID.** The user never has to re-link. They just click Deploy — the domain serves the latest version in the background. This is the magic of the loop.
7. Rollbacks also respect connected domains — restoring an older deploy repoints the domain to that CID.

### Backend to build
- **Supabase `domains` table:** `{ id, domain, project_id, owner_uid, current_cid, status: "verifying" | "active" | "error", verified_at, created_at }`
- **Ownership verification:** issue a DNS TXT record challenge (e.g. `_sherry-verify.yourdomain.pi = [one-time-token]`) the user adds, then check it server-side. Confirm the exact verification method against current Pi domain docs — **do not improvise the verification flow**.
- **Resolution:** map the `.pi` domain to the platform gateway via DNSLink (`_dnslink TXT → /ipfs/{CID}`) OR route by host header on the gateway. Verify which method Pi's domain system supports in current Pi docs before implementing.
- **Auto-update function:** called at the end of every successful deploy pipeline. Updates `current_cid` in the `domains` table for every domain attached to that project, then refreshes the DNSLink/host-header record. This one function is what makes "redeploy and it just works" true.
- **Rollback function:** when a user restores a previous deploy, run the same auto-update function against the restored CID.

## 6. PLATFORM ARCHITECTURE (build as independent, incrementally-shippable services)

**1. Content + permanence layer**
Static builds → IPFS, addressed by CID. Run the platform's own IPFS pinning node plus a fallback pinning service (e.g. Pinata or web3.storage as backup). On Pro and Business tiers, make **Filecoin storage deals** — this is what makes the "permanent, can't be deleted" promise technically true and justifies premium Pi pricing.

**2. Naming and resolver layer**
The `.pi` domain resolver from Part 5 handles custom domains. The platform also mints random `.pinet` subdomains for all users. Both map human name → latest CID. Every deploy updates the mapping.

**3. Deploy pipeline + CI/CD (the critical path)**
`upload → pin to IPFS → receive CID → provision SSL → update domain mappings → update project record → show reveal`
- Every deploy produces an immutable CID. **Instant rollback = repoint name to a previous CID** — one tap, zero re-upload, zero risk. IPFS gives you this almost for free. Ship rollbacks early — they are a killer feature.
- **Automatic SSL:** every deployment and every connected `.pi`/`.pinet` domain gets an SSL certificate provisioned automatically at the gateway/CDN layer (e.g. via Let's Encrypt / the CDN's managed certs). HTTPS is on by default — the user never configures it.
- **Git CI/CD:** offer a Git-connected path. When the developer pushes to a connected repo (branch), automatically build, deploy a new immutable CID, and generate an **instant preview deployment** with its own unique URL (one per branch/push) before promoting to production. **Deployments are unlimited and never frequency-capped** — quota is projects + storage + bandwidth only (Part 4).

**4. Edge functions (global, low-latency dynamic execution)**
Static assets live on IPFS; **dynamic logic runs on edge functions** executed close to the user for low latency (form handlers, lightweight APIs, server-side logic, redirects). Wire these so a hosted site can run server-side code without the developer standing up infrastructure. Gate richer edge usage by tier (Pro = standard, Business = higher limits/concurrency). This is what lets Sherry host real apps, not just static sites.

**5. Pi SDK baked into every hosted site**
Every site deployed on Sherry gets Pi auth + Pi payment widgets pre-wired via a platform JavaScript snippet. A developer deploys a site and can immediately charge visitors in Pi — without writing any payment code. **The platform takes its tier-based fee on every Pi transaction.** This is the moat: Sherry is the fastest way to launch a Pi-earning app.

**6. Marketplace / discovery layer**
A directory of live Pi apps deployed on the platform. All Builder+ tiers are listed. Business tier is featured (boosted placement). Submit, browse, search. Every site deployed advertises the platform to the next developer.

### Decentralization — the honest position (do not overclaim this)
**Genuinely decentralized and permanent:** content (IPFS/Filecoin CIDs), the domain mapping registry, rollback history. Sites cannot be taken down. Content cannot be altered. Users can always access their CID independently of Sherry. **This is real and must be literally true.**

**Practically centralized for now:** dynamic compute, Supabase database, Pi auth intermediation. This is fine — state it plainly.

**Positioning copy:** *"Decentralized and permanent where it counts. Your content is yours and can't be locked in — with a managed convenience layer you can leave anytime."* Build the "no lock-in" promise to be literally true. Never break it.

### 7.4 Create a payment (User-to-App flow)
This is how subscriptions and tier upgrades are charged. Call this from the client.

```ts
// lib/piPayment.ts
import { type PiEnv } from "./piEnv";

export function payWithPi(
  env: PiEnv,
  amountPi: number,
  memo: string,
  metadata: Record<string, unknown>
): void {
  (window as any).Pi.createPayment(
    {
      amount: amountPi,      // the Pi amount, e.g. 17 for Builder tier
      memo,                  // shown to the user, e.g. "Sherry Hosting — Builder plan"
      metadata: { ...metadata, env }, // attach env so the server knows which key to use
    },
    {
      // Step 1: Pi gives us a paymentId — pass to our server to approve
      onReadyForServerApproval: (paymentId: string) => {
        fetch("/api/pi/approve", {
          method: "POST",
          headers: { "Content-Type": "application/json" },
          body: JSON.stringify({ paymentId, env }),
        });
      },

      // Step 2: User signed the blockchain tx — pass paymentId + txid to complete
      onReadyForServerCompletion: (paymentId: string, txid: string) => {
        fetch("/api/pi/complete", {
          method: "POST",
          headers: { "Content-Type": "application/json" },
          body: JSON.stringify({ paymentId, txid, env }),
        });
      },

      // Payment was cancelled by the user
      onCancel: (paymentId: string) => {
        fetch("/api/pi/cancel", {
          method: "POST",
          headers: { "Content-Type": "application/json" },
          body: JSON.stringify({ paymentId, env }),
        });
      },

      onError: (error: any, payment?: any) => {
        console.error("Pi payment error:", error, payment);
        // Show a user-facing error toast, never a raw error string
      },
    }
  );
}
```

## 8. COLLABORATION, ROLES & ACTIVITY (Pi-native team layer)

Sherry is multi-user from day one — and collaboration is **Pi-native**: every collaborator is a KYC-verified Pi human, invited by Pi identity rather than email. That makes the team layer sybil-resistant and trustworthy in a way no generic host can match. Build these so projects can be shared, managed, and even monetized together safely.

### 8.1 Role-based access control (RBAC)
Three roles per project:
- **Owner** — full control: billing/subscription, delete project, manage members and roles, deploy, configure domains. One owner; ownership can be transferred.
- **Admin** — everything except billing and deleting the project: deploy, manage domains, invite/remove Members, view activity.
- **Member** — deploy and view only; cannot manage members, billing, or destructive settings.

Enforce permissions on the **server**, not just by hiding UI — every mutating API route checks the caller's role before acting. Store roles in a Supabase `memberships` table: `{ project_id, user_uid, role: "owner" | "admin" | "member", invited_by, joined_at }`.

### 8.2 Pi-native collaboration (invite by Pi identity, not email — this is the differentiator)
Because the Pi Network is KYC-gated, **every collaborator is a verified, unique human** — no fake emails, no bots, no sybils. Lean into this fully: collaboration uses Pi identities, not email/passwords.

**How it actually works (respecting how the Pi SDK behaves):** the Pi SDK is a *client-side* library that runs inside the Pi Browser, and it only ever exposes the **current authenticated user** — there is no public directory to look up or "reach out" to a Pi user who hasn't opened the app. So you don't invite outward; you let verified Pi users come *in*:
1. An Owner/Admin taps "Add collaborator" → the app generates a **tokenized project invite link**, optionally with a pre-set role (Admin/Member). Store it: `invites { project_id, token, role, status, expires_at }`.
2. The Owner shares the link (e.g. via Pi Chat). The invitee opens it **in the Pi Browser**.
3. The invitee taps **"Join with Pi"** → client-side `Pi.authenticate(["username"], ...)` runs → the app receives their verified `{ uid, username }` and an `accessToken`.
4. The client sends the `accessToken` + invite token to an **edge function / server route**, which validates the user by calling `GET https://api.minepi.com/v2/me` with `Authorization: Bearer {accessToken}`, confirms the invite token, then creates the membership keyed by the Pi **uid** with the invite's role.
5. Done — the collaborator is on the project, identified by their KYC'd Pi identity. No email, no password.

> Note: this is exactly where edge functions belong — the server-side **validation** of the joiner's Pi token (`/v2/me`) and, later, the payouts in 8.5. The *authentication* itself must happen client-side via `window.Pi` in the Pi Browser; an edge function cannot run the Pi SDK. If a future Pi platform API adds a username-lookup or direct-invite primitive, reach-out invites can be added then — **confirm against current Pi docs.**

### 8.2b Open collaboration via the marketplace (optional, powerful)
A project can be flagged "open to collaborators." Any Pi user browsing the marketplace (Part 6) can tap **"Request to collaborate"** → authenticates with Pi → an Owner/Admin approves the request, creating the membership. This turns the KYC'd Pi user base into a trusted collaborator pool — discovery and verified-identity trust in one.

### 8.2c Tier gating
Team/RBAC is a **Business-tier** capability (Part 4) — gate accordingly, but build the RBAC model for all tiers (every project has an Owner by default).

### 8.3 Activity log (real-time audit trail)
- Log every meaningful event: deploys, rollbacks, domain connect/remove, member invited/removed/role-changed, subscription/tier changes, settings edits.
- Supabase `activity` table: `{ project_id, actor_uid, action, detail (jsonb), created_at }`. Surface it as a reverse-chronological feed that updates in real time (Supabase Realtime).
- Each entry reads in plain language: "beejayy223 deployed to `merchanthub.pinet` · 2m ago", "Admin removed member alice · 1h ago".

### 8.4 Consolidated project dashboard
Tapping a project opens its dashboard — one screen with: live URL + status, latest deploy + deploy history (with rollback), connected domain(s), storage/bandwidth usage for that project, members + roles, and the activity feed. This is the per-project command center. Single-column and mobile-first like everything else.

### 8.5 Pi-native revenue sharing (the unique payoff — A2U payouts to collaborators)
Because every collaborator joined via Pi, you hold their verified Pi **uid**. That unlocks something no generic host can do: **split a site's Pi earnings among its collaborators automatically.**
- An Owner sets a split per project (e.g. 70% owner / 30% contributor), stored alongside memberships.
- When the site earns Pi (paywalls/tips from Part 4), the platform pays each collaborator their share via **App-to-User (A2U) payments**: server-side `POST https://api.minepi.com/v2/payments` with `{ amount, memo, metadata, uid }` for the recipient, then submit the blockchain transaction and complete it. A2U does **not** require the user-approval step (the app initiates it), but you must look up the recipient's account before each transaction. Follow Pi's A2U integration guide exactly — do not improvise the payout flow.
- Result: a hosting platform where a KYC'd team builds a Pi app together and the Pi revenue auto-splits to verified humans. This is the innovative, defensible feature — collaboration + monetization + Pi identity in one loop.
- Gate revenue-splitting to Business tier (or Pro+), since it depends on the team/RBAC layer.

## 10. COPY AND POLISH RULES

- **Sentence case everywhere.** No ALL CAPS in body copy. Buttons, labels, and toasts all use sentence case.
- **Plain verbs.** A button says exactly what it does: "Deploy," "Connect domain," "Copy URL," "Restore this version," "Upgrade with Pi." Not "Submit," not "Proceed."
- **Word consistency.** The word on the button matches the resulting toast. "Deploy" → toast says "Deployed." "Connect domain" → toast says "Domain connected."
- **Name by what the user controls, not how the system works.** Say "Your Pi domain" not "DNSLink record." Say "Permanent storage" not "Filecoin deal."
- **Empty states give direction.** Never "Nothing here yet." Always: one sentence of context + one action.
- **Error states give next steps.** Never a raw error string. Always: a human sentence + a retry/help action.
- **Loading states use skeletons.** Never a blank screen, never raw `undefined`, never `NaN`.
- **Every Pi amount is in `JetBrains Mono` with the π symbol.** Example: `10 π` not "10 Pi".
- **Every URL, CID, and `.pi` domain is in `JetBrains Mono`.** No exceptions.
