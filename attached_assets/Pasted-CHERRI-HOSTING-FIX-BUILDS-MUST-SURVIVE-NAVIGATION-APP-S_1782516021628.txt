CHERRI HOSTING — FIX: BUILDS MUST SURVIVE NAVIGATION / APP-SWITCHING (resume in-progress builds)

THE BUG: When a user starts a build on the deploy page and then navigates away (to Home, another tab, or backgrounds the app / switches to Pi Browser), the build state is lost. Returning to the deploy page shows a fresh empty page and the user has to start the entire upload+build over. The build job actually runs on the SERVER with a job ID (GET /builds/:jobId already exists), but the client forgets the job ID and stops polling.

THE FIX: Persist the in-progress build's job ID so the deploy page can RECONNECT to a still-running (or finished) build when the user returns — instead of restarting. Do NOT change the build engine or the pipeline; this is client-side persistence + reconnect, plus a small server confirmation if needed.

Run straight through. At the end run both TypeScript checks (zero errors) and report.

Since localStorage is the natural place but confirm what's allowed in this codebase — if localStorage is available use it; store { jobId, projectId, stage, startedAt }. Persist enough to restore the deploy page's stage state (which project, that a build is running, and the jobId to poll).

2. RECONNECT ON RETURN: when the Deploy page mounts, check for a persisted active build. If one exists:

If GET /builds/:jobId returns not-found, clear and reset cleanly.
